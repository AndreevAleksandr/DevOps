### Базовые понятия: Процессы

#### Что такое процесс?
> **Процесс** - это запущенная программа с выделенными ресурсами (Память, CPU). Понимание процессов = понимание того, почему сервер тормозит и как это чинить.

### Основные команды
- Снимок всех процессов в системе: ` ps aux `
- Уникальный номер процесса: ` PID `
- Завершить процесс (Отправляет SIGTERM): ` kill <PID> `
- Принудительно убить процесс (SIGKILL): ` kill -9 <PID> `

### Директория /proc
- Псевдофайловая система
- Вся информация о процессах в реальном времени 
- ` ps aux ` и ` htop ` берут анные именно  из ` /proc `
- Пример: ` /proc/<PID>/status ` - информация о процессе

### SystemD
> **SystemD** - система инициализации и управления службами в современных Linux-дистрибутивах.

### Основные команды
- Запустить сервис: ` systemctl start <сервис> `
- Остановить сервис: ` systemctl stop <сервис> `
- Перезапустить сервис: ` systemctl restart <сервис> `
- Добавить в автозагрузку: ` systemctl enable <сервис> `
- Убрать из автозагрузку: ` systemctl disable <сервис> `
- Показать статус сервиса: ` systemctl status <сервис> `
- Посмотреть логи сервиса: ` journalctl -u <сервис> `
- Следить за логами в реальном времени: ` journalctl -f -u <сервис> `

### OOM Killer (Out of memory Killer)
> Механизм ядра linux, который убивает процессы при нехватке RAM.

1. В системе заканчивается свободная память
2. Ядро выбирает "жертву" по ` oom_score ` 
3. Убивает процесс, чтобы спаси систему

- ` oom_score_adj ` можно настроить приоритет защиты (-1000 = никогда не убивать)

### Состояния процессов
- Выполняется: ` R ` (Running)
- Спит, ждет: ` S ` (Sleep)
- I/O блокировка (Стоит в очереди на ресурсы): ` D ` (Disk_sleep)
- Мертв, но запись о нем есть в таблице: ` Z ` (Zombie)
- Остановлен: ` T ` (stopped)

---

### Zombie-процессы
- Процесс завершен, но родитель не получаел его статус
- Не потребляет ресуры, но занимает место в таблице процессов
- **Решение:** убить родительский процесс или дождаться его завершения

### Утилиты диагностики

**vmstat** показывает статистику по памяти,процессам, I/O и CPU
- Обновления каждую секунду, 5 раз: ` vmstat 1 5 `
- С таймстампами: ` vmstat -t 1 `
- Active / Inactive memory: ` vmstat -a `
    - Процессы, готовые к выполнению: ` r (runnable) `
    - Процессы в состоянии D (Ждут I/O): ` b (blocked) `
	- Использовано swap: ` swpd `
	- Свободная RAM: ` free `
	- Кэш ядра: ` buff / cache `
	- Активность свопа (если больше 0-ля - нехватка RAM): ` si / so (swap in / out) `
	- Чтение / запись на диск: ` bi / bo (blocks in / out) `
	- CPU на пользовательские процессы: ` us (user) `
	- CPU на ядро (если больше 20% - возможно, слишком много системных вызовов): ` sy (system) `
	- CPU ждет I/O (если больше 20% - узкое место на диске): ` wa (wait) `
---
**iostat** для диагностики дисковой подсистемы
- Расширенная статистика каждую секунду: ` iostat -x 1 `
- Скрывает пустые устройства: ` iostat -xz 1 `
- Конкретный диск: ` iostat -p sda 1 `
    - Операция чтения / записи в секунду: ` r / s, w / s `
	- Килобайт в секунду: ` rkB / s, wkB / s `
	- Объедененные запросы (merged): ` rrqm / s, wrqm / s `
	- Процент времени, когда диск был занят: ` %util `
	- Среднее время отклика: ` await `
	- Отдельно для чтения / записи: ` r_await / w_await `

**Использование**
- %util больше 80% плюс высокий await - значит диск не справляется
- Если w_await больше r_await - значит проблема с записью
- Для баз данных: await больше 20mc - медленно
---
**sar** Сбор и анализ системной статистики по времени
- CPU загрузка (3 отчета с интервалом 1 сек): sar -u 1 3
- Использование памяти: ` sar -r 1 3 `
- I/O статистика: ` sar -b 1 3 `
- Сетевая статистика: ` sar -n DEV 1 3 `
- Вся статистика: ` sar -A `
- Вчерашний отчет: ` sar -f /var/log/sa/sa01

**Пример** Найти пиковую нагрузку CPU за вчера
sar-f/var/log/sa/sa15 | grep -A1 "Average" | head -20

**Использование**
- Ретроспективный анализ: "Почему сервер тормозил вчера?"
- Планирование ресурсов: тренды использования CPU / RAM
- Доказательство проблем
---
**dstat** Универсальный мониторинг
- Базовые вывод: ` dstat `
- CPU, Disk, Network, Memory: ` dstat -c -d -n -m `
- Таймстамп + топ CPU процесса: ` dstat -t --top-cpu `
- Топ по памяти: ` dstat -t --top-memory `
- Экспорт в CSV: ` dstat --output file.csv `

**Использование**
- Один инструмент вместо пяти

**pidstat** Статистика по отдельным процессам
- Все процессы: ` pidstat 1 `
- Конкретный PID: ` pidstat -p 0000 1 `
- I/O по процессам: ` pidstat -d 1 `
- Память по процессам: ` pidstat -r 1 `
- CPU по всем процессам: ` pidstat -u -p ALL 1 `
- Переключения контекста: ` pidstat -w 1 `

- Чтение с диска: ` kB_rd/s `
- Запись на диск: ` kB_wr/s `
- Задержка I/O: ` iodelay `

**Использование**

- Определить какой процесс создает нагрузку на CPU

### Память
` free -h `

**Virtual Memory Size**
- Вся вирутальная память процесса (Включая swapped out и не выделенную)
- Показывает: ` ps aux | grep <process>
---
**Resident Set Size**
- Реальная физическая RAM, которую использует процесс
- Не включает swap и page cache
- Показывает: ` ps aux ` (колонка RSS, в KB)
---
**Shared Memory**
- Память, которую используют несколько процессов
- Показывает: ` ps aux ` (колонка SHR)
---
**Page Cache** - Кэш ядра Linux для файловых операций
1. При чтении файла с диска, Linux кэширует его в RAM
2. При следующем чтении - данные берутся из RAM
3. При записи - данные сначала в cache, потом асинхронно на диск

``` 
	free -h			# колонка buff/cache
	cat /proc/meminfo | grep -E 'Cached|Buffers'
```
**Важно понимать:**
- Cached не равно Used - Page cache автоматически освобождается, когда приложениям нужна память
- available больше free (free показывает только полностью свободную RAM)

### Сеть: утилиты и мониторинг
**ss** - Современная замена netstat
- Все слушающие TCP/UDP порты: ` ss -tuln `
- Плюс процессы: ` ss -tulnp `
- Общая статистика: ` ss -s `
- Установленные соединения: ` ss -o state established `
- Использование памяти сокетом: ` ss -m `

**Фильтры**
- Соединения с конкретным IP: ` ss dst 192.168.0.1 `
- Источник порта 443: ` ss sport = :443
- Соединения в TIME_WAIT: ` ss state time-wait `
---
**netstat** - Устаревшая утилита
- Слушающие порты: ` netstat -tulnp `
- Все соединения: ` netstat -an `
- Статистика по протоколам: ` netstat -s `
- Интерфейсы: ` netstat -i `
---
**iftop** - Мониторинг сетевого трафика в реальном времени
- Базовый запуск: ` iftop `
- Конкретный интерфейс: ` iftop -i eth0 `
- Не разрешать имена: ` iftop -n `
- Не разрешать порты: ` iftop -N `

**Использование**
- Найти, кто грузит сеть
- Увидеть, куда уходит трафик
- Определить пиковую нагрузку на интерфейс
---
**nload** - Графический мониторинг общего трафика
- Конкретный интерфейс: ` nload eth0 `
- Несколько интерфейсов: ` nload -m `
- В MB/s: ` nload -u M `

**Использование**
- Общий мониторинг загрузки канала
- Увидеть пики трафика
- Понять, хватает ли пропускной способности
---
**tcpdump** - перехват пакетов
- Трафик на 80 порту: ` tcpdump -i eth0 port 80 `
- С конкретным хостом: ` tcpdump -i eth0 host 192.168.0.1 `
- Запись в файл: ` tcpdump -i eth0 -w capture.pcap `
- Только SNY пакеты: ` tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0' `
---
**iperf3** - тест скорости
- На сервере: ` iperf3 -s `
- На клиенте: ` iperf3 -c 192.168.0.1 `
---
**nmap** - сканирование портов
- Сканирование портов: ` nmap -p 1-1000 192.168.0.1 `
- Определить версии сервисов: ` nmap -sV 192.168.0.1 `
- Определить OC: ` nmap -O 192.168.0.1 `
---
**dig / nslooku** - DNS диагностика
- DNS запрос: ` dig example.com `
- Только IP: ` dig +short example.com `
- MX запись: ` dig MX example.com `
- Альтернатива dig: ` nslookup example.com `

### Perf и профилирование

- Real-time просмотр: ` perf top `
- Конкретный PID: ` perf top -p 0000 `
- С call graph: ` perf top -g `
- Сгруппировать по процессам: ` perf top --sort comm `

**Использование**
- Найти "горячие" функции в приложении
- Понять, почему процесс грузит CPU
- Оптимизиация
---
**perf record + report** - Запись и аналог производительности

- Проанализировать: ` perf report `
- Сгенерировать отчет: ` perf report --stdio > report.txt

**Использование**
- Профилирование продакшена без остановки
- Поиск узких мест в коде
- Доказательство

### Логирование
**journalctl** - Централизованное логирование в Linux

- Все логи: ` journalctl `
- Follow (как tail -f): ` journalctl -f `
- Логи сервиса nginx: ` journalctl -u nginx `
- Follow конкретного сервиса: ` journalctl -u nginx -f `
- За последний час: ` journalctl --since "1 hour ago" ` / ` journalctl --since "2026-09-09 14:00:00" --until "15:00:00"
- Только ошибки: ` journalctl -p err `
- Логи текущей загрузки: ` journalctl -b `
- Логи предыдущей загрузки: ` journalctl -b -1 `
- Список загрузок: ` journalctl --list-boots `
- С расширенной информацией: ` journalctl -xe `
- По тегу (program name): ` journalctl -t sshd `
- По PID: ` journalctl _PID=0000 `
- Сколько места занимаются логи: ` journalctl --disk-usage `
- Очистить, оставив 100MB: ` journalctl --vacuum-size=100M `

**Использование**
- Быстрый поиск проблем: ` journalctl -p err --since "10 min ago" `
- Расследование инцидентов: ` journalctl -b -1 | grep -i error
- Мониторинг в реальном времени: ` journalctl -f -u myapp

### Вопрос - ответ
- Что такое Load Average?
    - Средняя нагрузка на систему за 1, 5, 15 минут
    - Показывает количество процессов в состоянии R (running) и D (uninterruptible sleep)
    - Если load average больше количества ядер CPU это значит, система перегружена
- Что такое inodes, зачем нужны?
    - Структуры данных, хранящие метаданные о файлах (права, владелец, расположение блоков на диске)
    - Ошибка "No space left on device" может быть не из-за нехватки места, а из-за нехватки inodes
    - Проверить: ` df -i `
- Что такое Zombie-процесс?
    - Процесс завершён, но родитель не прочитал его статус через wait()
    - Не потребляет ресурсы, но занимает запись в таблице процессов
    - **Решение:** убить родительский процесс
- Ошибка "No space left on device",но место на диске есть. В чем причина?
    - Закончились inodes (слишком много мелких файлов)
    - **Проверить:** ` df -i `
    - **Решение:** удалить лишние файлы или увеличить раздел
- Опишите загрузку системы Linux от включения питания до появления приглашения в систему
    - BIOS/UEFI → Bootloader (GRUB) → Ядро Linux → initramfs → systemd → target (multi-user/graphical) → login
- Какие сигналы процессов тебе известны?
    - Мягкое завершение: ` SIGTERM(15) `
	- Жесткое завершение: ` SIGKILL(9) `
	- Перезапуск: ` SIGHUP(1) `
	- Ctrl + C: ` SIGINT(2) `
- Что означают права доступа 755 для директории?
    - Владелец: ` read+write+execute (7) `
	- Группа: ` read+execute (5) `
	- Остальное: ` read+execute (5) `
- Что такое LVM и зачем он нужен?
    - Logical Volume Manager - гибкое управление дисками
    - Позволяет динамически изменять размер разделов, создавать снимки (snapshots)
    - Абстракция между физическими дисками и файловыми системами
